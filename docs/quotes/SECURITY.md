# Security of the quotation system

The review done in PROMPT 21, written as what each control is, where it lives and which test would fail if it went. Nothing here weakens the content security policy, the administrators' sign-in, the session protection or the rate limits; none of them was changed. This is a code review plus automated and browser tests on a throw-away server. **It is not a penetration test**, and it says so in §3.

## 1. Controls, one risk at a time

| Risk | Control | Where | Test |
| --- | --- | --- | --- |
| **A customer reaching another customer's request or quotation (IDOR)** | no public address takes a reference, an e-mail address or an identifier: only a secret of 256 random bits, stored only as its SHA-256, bound to **one request or quotation and one action**. A status link opens only the status page, a quotation link only that quotation, a button only its own action | `quotes/tokens.ts`, `quotes/customer.ts` | `quoteIntegration.test.ts` *opens nothing of anyone else's, nothing with the wrong kind of secret*; `quotation.test.ts` *is no key to anything* |
| **Telling a real link from a made-up one** | an unknown, malformed or wrong-kind secret gets the same 404 in the same words; 20 failed lookups per address in 15 minutes then wait (429). The lookup is by the hash of the secret in an indexed column, so there is no secret-dependent comparison to time | `customer.ts` `missed`, `rateLimit.ts` | `quotationFlow.test.ts` *counts the guesses of a stranger*; the wrong-guess test above checks the words are identical |
| **Using a link after it should be dead** | a replaced, withdrawn, cancelled or **administrator-ended** link answers 410; an expired one 410; a spent button 409. A new version ends the old one's links in the same transaction that sends it | `lifecycle.ts`, `admin.ts` `revokeLinks` | `quotationFlow.test.ts` *stops a link that was replaced, withdrawn, expired or spent*; `quoteIntegration.test.ts` *ends the status page, the quotation page and the buttons…* |
| **Accepting by accident or by forgery** | opening a page or reading an e-mail accepts nothing; each button is a **separate single-use token** (2 hours) handed out when the page is opened; accepting needs a ticked confirmation; the amount, the status and the identity of the quotation come from the database, never from the request. Of two simultaneous clicks exactly one wins | `customer.ts` `act` | `quotationFlow.test.ts` *lets only one of two simultaneous acceptances through*; `quoteIntegration.test.ts` *does not take an amount, a total, a status or an owner from the customer's action* |
| **A browser telling the server a price, a total, a type, a source or a complexity** | all ignored: prices come from the catalogue, totals are summed from integer minor units on the server, the type and source are worked out, the project size guide is computed on the server (and compared with the website's copy over thousands of combinations) | `quotes/service.ts`, `shop/estimate.ts`, `money.ts` | `quotationFlow.test.ts` *works out the type of request itself and ignores anything the browser says*; `contract.test.ts` |
| **Unauthorised use of the administration** | every business function calls `requirePermission` (read / write / delete) itself, so a new route cannot forget it; sessions are server-side, `Secure`, `HttpOnly`, `SameSite=Strict` | `auth/permissions.ts` | `quotationFlow.test.ts` *refuses the unauthorised*; `quoteIntegration.test.ts` for the two new routes; the security probe calls **every** administration route with no session |
| **CSRF** | every state-changing administration request needs the session's CSRF token (403 without it), plus same-origin checks. The customer's endpoints are not cookie-authenticated, so a forged cross-site request has nothing to ride on: it would need the secret | `http/` | `auth.test.ts` *need the session's CSRF token*; `quoteIntegration.test.ts` (403 without the token on the two new routes) |
| **Script injection (XSS)** | the website renders everything as text (React); the e-mails put every typed value through an escaper or print it as text; the customer's text is shown with its line breaks, never as markup; the content security policy is unchanged | `lib/html.ts`, `notifications/templates.ts` | `quotationFlow.test.ts` *escapes what a person typed*; `quoteIntegration.test.ts` (the receipt for a change request, in three languages) |
| **Secrets leaking through logs, history, analytics or referrers** | the request log writes the **route pattern**, not the address; bodies are never logged; the logger masks keys and long tokens; the history holds fixed phrases only; the private pages are served `Cache-Control: no-store`, `X-Robots-Tag: noindex, nofollow`, `Referrer-Policy: no-referrer`; the page tracker strips the secret from the address it reports | `app.ts`, `lib/logger.ts`, `quotes/events.ts`, `_headers` | `quoteIntegration.test.ts` *is written nowhere it could be read back*; `quotationFlow.test.ts` *answers any secret with the same quiet shell, never cached, never indexed* |
| **Bypassing the rate limits** | per-client buckets keyed by a **keyed hash** of the address (the address itself is not kept): the request form 5 per 15 minutes, the customer's pages 90 per minute, wrong links 20 per 15 minutes, sign-in and the administration their own | `http/rateLimit.ts` | `security.test.ts`, `quotationFlow.test.ts` |
| **Duplicates** | content fingerprint for the public form; database-enforced once-only e-mails; one message → one request; one draft and one sent version per request (partial unique indexes) | see `WORKFLOW.md` §4 | `quotationFlow.test.ts`, `quoteIntegration.test.ts` |
| **Invalid status moves** | one transition table; the same check in the API and the interface; `quote_sent` only by sending; Accepted / Declined by hand need a note | `quotes/status.ts` | `quotation.test.ts` *has the ten stored statuses, each move checked* |
| **Header injection** | names and subjects are collapsed to one line before they reach a header; the MIME builder refuses a line break in an address or a header (and the message is not retried: it cannot become valid by waiting) | `notifications/mime.ts` | `quotationFlow.test.ts` *keeps the subject on one line*; `email.test.ts` |
| **A tampered database or a hand-edited migration** | a sent quotation and its lines are frozen by triggers; the history cannot be updated or deleted; a migration edited after it ran stops the server (checksum) | `migrations/0007`, `migrate.ts` | `quotationFlow.test.ts` *makes a sent version impossible to edit… in the database*; `quotation.test.ts` (migrations 0007 and 0009) |
| **Retention and erasure** | the owner chooses `RETENTION_DAYS`; spent and expired links are purged 30 days after they stop mattering; one request can be deleted and one address erased, including the owner's alerts about them | `system/maintenance.ts` | `quotationFlow.test.ts` *removes the request, its offers, links and e-mails on deletion*, `quoteIntegration.test.ts` *takes its alerts away with the request* |
| **A forged "delivered"** | only a webhook whose signature verifies (HMAC over the exact bytes, five-minute tolerance) can move a message to delivered, bounced or complained; a replayed event changes nothing | `notifications/webhook.ts` | `webhook.test.ts`, `quoteIntegration.test.ts` *is raised by a verified bounce or complaint, and by nothing else* |

## 2. What PROMPT 21 changed on the security side

* **A new action** to end every link a customer holds (administrators and editors; session, CSRF and permission checked; recorded in the history and the audit log; idempotent). It exists because until now the only ways to end a link were side effects of withdrawing, replacing or cancelling.
* **A new route in the security probe** (`/api/admin/quote-requests/:id/revoke-links`): all administration routes are called without a session and may only answer 401, 404 or 405.
* **Alerts about failed deliveries** carry no secret and no message text: the alert says which kind of message, to which address, and what the provider reported (with addresses and long tokens masked).
* Nothing was loosened: the content security policy, the sign-in, the sessions and the limits are exactly as before.

## 3. What is not covered, and the risks that remain

1. **A link is a bearer secret.** Anyone who has the e-mail has the link, and can accept the offer. That is the design of a link-based flow (there is no customer account), and the controls above reduce it (expiry, single-use buttons, the explicit confirmation, a keyed hash of the address recorded with an acceptance, and now the administrator's "end the customer's links"), but they cannot remove it. A compromised mailbox is a compromised link.
2. **The secret is in the address.** The application never logs it, but **the host and the proxy in front of it are outside this code**: Render's and Cloudflare's own access logs may record the path. This was not looked at (no access to either). Decide whether those logs are kept and for how long.
3. **The rate limiter is in memory, per process.** It resets when the server restarts and does not span several instances. Behind a proxy it sees the visitor's address only when `TRUST_PROXY` is set correctly; if it is not, every visitor looks like the proxy and the limits become global rather than per client (the platform audit, `docs/audit/`, lists this as an owner item).
4. **No penetration test, no fuzzing campaign, no third-party review.** The probe (`tools/e2e/security-probe.mjs`) and the tests are what was run.
5. **E-mail authentication is not set up for the domain** (see `EMAILS.md` §5). Without SPF, DKIM and DMARC a mail that carries a customer's link may be rejected or filed as spam, and the domain is easier to spoof.
6. **The webhook secret and the provider key live in the environment.** Rotating either needs a restart; nothing here stores them in the database or in a `VITE_` variable.
7. **Real-provider behaviour** (a real bounce, a real complaint) was exercised only against a signed mock of the provider's events, never against the provider.
