# Backend architecture (PROMPT 12)

Written **before** the implementation, from an audit of the repository on 2026-11-03. It says what exists, what was decided and why. Where the implementation had to deviate, `docs/backend/README.md` says so (that file is the operating manual: configuration, endpoints, admin, deployment, test results).

## 2. Decisions

1. **One new backend, in `server/`; nothing else to extend.** Node 22 (the installed runtime is 22.23; `engines` will say `>=22.18`), TypeScript run **natively** (type stripping, no build step), **zero runtime dependencies**: `node:http`, `node:sqlite`, `node:crypto` (scrypt, HMAC, random), `node:net`/`node:tls` (SMTP), global `fetch`. Dev dependencies stay as they are (vitest, TypeScript already exist). Rationale: "no unnecessary dependencies"; a portfolio site's backend is small and a dependency tree is the largest part of a small server's attack surface.
2. **Database: SQLite via `node:sqlite`**, WAL mode, foreign keys on, one file. It is the smallest relational database that runs where this site will realistically be hosted (one small Node process with a persistent disk), needs no extra service and gives real constraints, indexes and transactions. **Trade-off, stated plainly:** `node:sqlite` is marked experimental by Node (it prints one `ExperimentalWarning`; the API has been stable but may change in a later Node major). All SQL access goes through `server/src/db/database.ts` (about 80 lines), so replacing it with `better-sqlite3` or a PostgreSQL driver touches one file plus the few SQLite-specific statements in the migrations. SQLite is a single-writer, single-host database: more than one server instance, or a host without a persistent disk, needs the PostgreSQL port (documented, not built: nothing here needs it).
3. **Migrations:** numbered `.sql` files in `server/src/db/migrations/`, applied in order inside a transaction each, recorded with a checksum in `schema_migrations`; a changed or failing migration stops start-up and leaves the database at the previous version. Run by `npm run server:migrate` and automatically at start-up unless `MIGRATE_ON_START=false`.
4. **Server rendered admin at `/admin`**, plain HTML forms, one small stylesheet, **no client-side script** (so the admin's Content-Security-Policy is `script-src 'none'`). It is separate from the public site in every way that matters: its own path, its own CSP and `noindex`, its own cookie (`__Host-` prefixed, `HttpOnly`, `SameSite=Strict`, `Secure` in production), CSRF tokens on every form, backend permission checks on every route. A React admin would add a second build, a bundle and an XSS surface for a dozen screens.
5. **Authentication:** email + password for admin users created only from the command line (`npm run server:admin create`), no public registration. Passwords: `scrypt` (N=2^15, r=8, p=1, per-user random salt, constant-time compare), minimum 12 characters. Sessions: random 256-bit token in the cookie, **only its SHA-256 stored**, absolute and idle expiry, rotated on login, deleted on logout and on password change. Roles: `admin` (everything) and `editor` (requests and content; no deletion, no system pages).
6. **Public API under `/api`**, JSON, one envelope (`{data}` / `{error:{code,message,details?,requestId}}`), explicit CORS allow-list, no cookies on public endpoints (the public site stays cookie-free: the privacy notice remains true). Rate limiting and abuse controls are in-process (a fixed-window limiter per client IP and route class): correct for one instance, documented as such.
7. **No server-side cart.** The cart is choices only, anonymous, in the visitor's browser; a quote request carries the whole selection and the server validates it against the catalogue. A server cart would need sessions or accounts for no gain ("do not require registration to request a quote").
8. **No payment, no fixed-price checkout.** Every price in the catalogue is a quote today. The schema and the API support published prices (`from`, whole units, currency, VAT mode) and **never read a price from a request**; the server's `shop/pricing` module computes the only totals there are (a quote request's fixed-price subtotal, empty while nothing is published).
9. **No file uploads, no media table.** No existing feature collects a file (the Lab's saved works are browser-local and never uploaded), so none is built. The `media_assets` table of the brief is deliberately not created.
10. **Email:** a provider interface with `smtp` (own minimal client: implicit TLS or STARTTLS, `AUTH PLAIN/LOGIN`, UTF-8 MIME, dot-stuffing), `file` (writes `.eml` files; development) and `none` (default: nothing is sent, and the admin says so). Mail is queued in an **outbox table** and sent after the visitor's request has been answered; failures are retried with back-off (the log keeps attempts and a sanitised error). "Accepted by the provider" (SMTP 250) is the strongest claim the system ever records; **nothing says "delivered"**. Templates in `hu`/`en`/`nl`, HTML + text, branded. Owner notifications go to `NOTIFY_TO` (never invented); customer notifications exist only for **status changes initiated by an administrator** (no automatic confirmation to an address an anonymous visitor typed: that is a mail-bombing vector).
11. **Catalogue content lives in the database; the static site is generated from it.** The existing trilingual TypeScript stays the *seed* (exported to JSON by `scripts/export-catalog-seed.mjs`, a test keeps the JSON equal to the source). The admin edits prices, texts, status and associations. The public site is static, so edits reach it at **build time**: `npm run catalog:pull` fetches `/api/shop/catalog` into `src/content/catalog.generated.json`, which the content modules merge over the static text and prices; the admin's "Publish" button calls an optional deploy hook (`DEPLOY_HOOK_URL`). This keeps the prerendered, SEO-friendly pages and adds no runtime flash of old content. **Limits:** only entities the site code knows (the four services, four packages, eight add-ons, the FAQ ids) are shown by the site; a service created in the admin exists in the API and accepts quote requests, but has no page until the frontend gets one; "disable" is enforced by the server (requests refused) while the page stays until the next build. The API itself is complete and tested.
12. **Contact and quote forms use the existing transports unchanged**: the frontend only needs the endpoint (`VITE_API_URL`, or the two existing endpoint variables). Their contract (`form: 'contact' | 'quote'`) is the API contract; the server re-validates everything.
13. **Observability:** structured JSON logs to stdout (request id, route, status, duration; never bodies, passwords, tokens, or e-mail addresses), `GET /api/health` (liveness) and `GET /api/ready` (database reachable, migrations current, e-mail configuration state), process-level handlers, graceful shutdown, an admin "System" page with counters (requests, errors, e-mail queue) read from what is stored or counted since start-up.
14. **Privacy and retention:** only what the forms already collect is stored. A configurable retention (`RETENTION_DAYS`) deletes closed or archived requests and old delivery logs; an administrator can delete a record permanently; `npm run server:admin erase <email>` removes everything about an address. The network address of a submitter is stored only as a keyed hash (abuse correlation), never in clear text. Logs carry no personal data. This is technical infrastructure for a notice and a policy; it is not a legal assessment.

## 3. Module map

`server/src/`

| Module | Responsibility |
| --- | --- |
| `main.ts`, `app.ts`, `cli.ts` | Start-up and shutdown; the composition root (`createApp({config, db, mailer, clock})`, which tests use with an in-memory database); command line tasks. |
| `config.ts` | Reads and validates the environment once; refuses to start on a bad value with a message naming the variable; a redacted view for the admin page. |
| `http/` | Router, body reading with size limits, response envelope, error classes and codes, security headers, CORS, rate limiter, client address, request id, cookies, logging. |
| `db/` | `database.ts` (the only file that knows `node:sqlite`), `migrate.ts`, `migrations/*.sql`, `seed.ts`. |
| `modules/contact` | `POST /api/contact`: validation, spam checks, duplicate detection, storage, notification. |
| `modules/inquiries` | Inquiry data access and the admin's list/detail/status/notes/archive operations. |
| `modules/quotes` | `POST /api/quote-requests`: validation against the catalogue, storage of items and extras, server-side totals; admin operations, export. |
| `modules/catalog` | Services, packages, extras, categories, FAQ, localised read models for the public API; admin CRUD with validation of prices and translations. |
| `modules/shop` | `/api/shop/*` read endpoints and the aggregate catalogue; pricing rules (`pricing.ts`). |
| `modules/content` | Site content blocks (FAQ, text, project presentation) with translations. |
| `modules/auth` | Passwords, sessions, login throttling, CSRF, permissions. |
| `modules/admin` | HTML views and form handlers for the dashboard, inquiries, quote requests, catalogue, content, system. |
| `modules/notifications` | Provider interface, SMTP client, templates (hu/en/nl), outbox with retry, delivery log. |
| `modules/system` | Health and readiness, retention and maintenance, audit log, counters. |

Layering inside a module: `routes.ts` (HTTP only) → `service.ts` (business rules, transactions) → `repository.ts` (SQL) with `validation.ts` beside them; nothing in `routes.ts` touches SQL and nothing in `repository.ts` knows HTTP.

## 4. Data model (migration `0001`)

`schema_migrations` · `admin_users` · `admin_sessions` · `inquiries` · `inquiry_notes` · `quote_requests` · `quote_request_items` · `quote_request_item_extras` · `quote_request_notes` · `services` · `service_translations` · `packages` · `package_translations` · `package_needs` · `package_extras` · `service_packages` · `extras` · `extra_translations` · `extra_needs` · `site_content` · `site_content_translations` · `email_deliveries` · `audit_log`.

Conventions: identifiers of customer-facing records are random text (`reference` is a short code shown to the visitor, never an incrementing number); timestamps are UTC ISO-8601 text; every foreign key is declared and enforced; enumerations are `CHECK` constraints; a published `from` price must have an amount, a currency and a VAT mode other than `unspecified` (a `CHECK`, mirroring the frontend test); catalogue rows that requests refer to are disabled, never deleted (`ON DELETE RESTRICT`); indexes cover every list, filter and foreign key the application uses.

## 5. API surface

Public: `GET /api/health`, `GET /api/ready`; `POST /api/contact`; `POST /api/quote-requests`; `GET /api/services`, `/api/services/:slug`; `GET /api/packages`, `/api/packages/:code`; `GET /api/shop/services`, `/api/shop/packages`, `/api/shop/extras`, `/api/shop/categories`, `/api/shop/catalog` (everything, all languages, with a version hash and an ETag); `GET /api/content/faq`.

Admin (session cookie + CSRF, under `/admin`, HTML) and the JSON mirror under `/api/admin/*` for the operations the brief names (`GET /api/admin/inquiries`, `GET /api/admin/quote-requests`, `PATCH /api/admin/inquiries/:id`, `PATCH /api/admin/quote-requests/:id`, catalogue and content CRUD): the JSON admin API requires the same session and a CSRF header, so it can never be called by another site.

Request and response formats, validation rules and error codes are written next to the code in `docs/backend/README.md`.

## 6. Security model (summary)

Secrets only from the environment, validated at start-up, never logged, never returned. Every input is validated on the server against explicit rules and length limits and stored with parameterised SQL only; every output in the admin is escaped by a single `html` tagged template; public responses never include customer data. Headers: strict CSP (`default-src 'none'` for the API; `script-src 'none'` for the admin), `nosniff`, `Referrer-Policy: no-referrer`, `frame-ancestors 'none'`, `Cache-Control: no-store` on anything personal. CORS: exact origins from `CORS_ORIGINS`, no wildcard, no credentials on public endpoints. Abuse: per-IP rate limits (contact, quote, catalogue, login), a login lockout per account, a honeypot field and a minimum fill time accepted by the contact/quote endpoints, duplicate-submission detection, body size limit (64 kB), JSON-only. Errors: one envelope, no stack traces or internals in any response.

## 7. Test plan

Vitest against a real in-process server and a real (in-memory or temporary-file) SQLite database, plus a real mock SMTP server on a local port. Functional: contact, validation, storage, quote requests, catalogue reads, pricing, e-mail, login, authorisation, status changes, content management, migrations. Security: unauthenticated and wrong-role admin access, CSRF, SQL injection strings, stored XSS rendered in the admin, rate limits, session expiry/logout/fixation, CORS, secrets never in responses or logs. Reliability: database unavailable, SMTP unavailable (submission still stored, delivery retried), invalid configuration, duplicate submissions, a failing migration. A clean-start check runs the real server process in an empty directory. What cannot be verified here (a real SMTP provider, TLS to one, a production host) is listed as such.

## 8. What changed while building it

Recorded so the plan above is not read as the result. The operating manual (`README.md`) describes what exists.

- **Consent became part of the payload.** The plan said the consent tick was *not* sent. The backend has to be able to insist on it and to record when it was given (`REQUIRE_CONSENT`, `consent_at`), so both request builders now send `consent` (a two-line change in `contact/validation.ts` and `shop/inquiry.ts`, tests updated); nothing else in the website's request changed.
- **Spam controls:** the honeypot field (`website`) and the link counter exist on the server; the **minimum fill time** in the plan was *not* built (it needs the form to send a start time), and the website's forms do not send the honeypot either. Rate limits, duplicate detection, link counting and the body limit are what is active.
- **Admin CSP** is `default-src 'none'; style-src 'self'; img-src 'self' data:; form-action 'self'; base-uri 'none'; frame-ancestors 'none'`; no `script-src` is needed because there is no script.
- **Module layout** is simpler than the map in §3: `modules/content` does not exist (FAQ and content blocks live in `modules/catalog`), contact has `service.ts` + `routes.ts`, and the admin operations sit in each module's `admin.ts`. The layering rule (HTTP → business rules → SQL) holds.
- **Decision 11 (catalogue → website)** is implemented as `src/content/catalogOverlay.ts` + `scripts/pull-catalog.mjs`, with the limits stated there made concrete: prices, VAT, texts and `featured`/`quoteRequired` of the packages and add-ons the website already has, and the whole FAQ, reach the site; which packages, add-ons and services *exist*, and the service pages' texts, stay in the website's source. Disabling a package in the administration therefore stops the backend taking requests for it at once, while the website keeps offering it until its source is changed.
- **Added during the work:** `npm run server:backup` (a consistent copy of a live database), the keyed (HMAC) duplicate fingerprint, static serving of hidden or non-website files refused, `Origin: null` handling for the admin's own forms, the same-origin allowance for a website served by this process, `catalog:pull --check/--remove`.
- **Status e-mails to customers** are one-per-click from the administrator, as planned; nothing is sent automatically to an address a visitor typed.
- **Not done:** deployment to a host, a real SMTP provider, accessibility audit of the administration, load measurement — see "What was not verified" in `README.md`.
