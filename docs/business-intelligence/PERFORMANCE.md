# Performance

Measured by `server/test/analyticsPerformance.test.ts` on a **synthetic** dataset generated by `server/test/analyticsSynthetic.ts`. The data is labelled (`SYN-…`, `SYNTHETIC`), deterministic, written only into the in-memory database of the test (or, for the browser checks, into a throw-away scratch database) and never into the application's own database, seed or migrations.

## The dataset

| Table | Rows | Table | Rows |
| --- | ---: | --- | ---: |
| quote requests | 25,000 | conversations | 5,000 |
| quotations (≈55 % of requests, two currencies) | ≈ 13,800 | conversation messages | 150,000 |
| quote events | ≈ 55,000 | consultations | 9,000 |
| customers | 6,000 | AI ledger rows | 70,000 |
| projects (8,000 + ≈ 3,300 made from accepted quotations) | ≈ 11,300 | AI tool calls | ≈ 23,000 |
| milestones / tasks | 14,000 / 50,000 | | |

That is far beyond what one studio produces in years; it is a scale test, not a forecast. Generating it takes ≈ 9 s.

**Correctness at this size** is checked too: the accepted value per currency and the funnel's first and "sent" stages equal direct `COUNT`/`SUM` queries on the stored rows.

## The bottleneck that was found, and how it was fixed

The first version built every time series by joining each bucket to the table (`FROM buckets JOIN rows ON at >= start AND at < end`). SQLite cannot use one index for that and read the table once per bucket:

| | first version | after |
| --- | ---: | ---: |
| financial, last 30 days | 818 ms | 80 ms |
| financial, 5 years | 1,865 ms | 197 ms |
| communication, last 30 days | 3,061 ms | 833 ms |
| communication, 5 years | 6,615 ms | 1,550 ms |

Two changes, both in the queries (no index, no migration): (1) the rows of the whole period are read once into a materialised CTE, and (2) each row is given its bucket in **one sorted pass** — the bucket starts and the rows are ordered together and every row takes the running maximum bucket key (`MAX(day) OVER (ORDER BY at, ord)`). One sort of *rows + buckets* instead of *rows × buckets* comparisons; the result is identical (the unit tests compare series with what was put in).

## What remains the slowest, and why that is acceptable

`communication` is the heaviest section: the customer-visible message tables are scanned a handful of times (counts, the time-to-reply window query, the volume series), and `conversation_messages` has no index on `created_at`. At 150,000 messages it still answers in 0.8–1.6 s. A real studio has orders of magnitude fewer messages. **If it ever matters**, an index on `conversation_messages(created_at)` would be the first thing to add — as a new migration, after measuring on the real database. It was not added: nothing measured justifies a migration on a database that is not that large.

## Why there is no cache

A cache would need invalidation across about ten tables and could show stale money or a stale backlog. Every answer is computed when asked, is never cached by the browser (`private, no-store`), and states when it was computed.

## Bounds

* A custom period is at most 1,830 days; daily points for up to 62 days, monthly beyond — at most about 62 points per series.
* Lists are bounded in SQL: alerts 25 per rule and 100 in all, AI tool usage 40, AI errors 20, interest lists 20, workload and deadlines a few dozen rows. No whole table is sent to the browser, and the browser computes nothing but formatting.
* The `analytics` rate limit (60 requests per minute) applies to both endpoints.
