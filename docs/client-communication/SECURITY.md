# Security

What protects a conversation, where the protection is, which test breaks if it goes, and what is **not** protected against. Nothing here is a claim that the system is production-ready: it was tested locally (TEST_RESULTS.md) and has had no independent review or penetration test.

## The measures

| Risk | Measure | Where | Tested by |
| --- | --- | --- | --- |
| **Ownership / IDOR** (a customer reaching another customer's conversation, message, project or marker) | Every customer endpoint looks the conversation up **through the session's customer id** (`reference = ? AND customer_id = ?`); a conversation of someone else, a missing one and a thread with nothing visible in it are the same `404`. A record a conversation is *about* is looked up through the customer too (`resolveContext`). References are random (`MSG-` + random), never counters. Every message id in the owner's `PATCH`/`DELETE` is looked up *inside the conversation and as the owner's own*. | `customer.ts`, `service.ts` | `communicationsSecurity.test.ts` ("another customer gets the same answer…", "who writes, which customer … are never believed"), the journey's step *"another customer cannot reach a conversation that is not theirs"* |
| **No sign-in / wrong kind of sign-in** | Customer endpoints need the customer's session; owner endpoints the administrator's, with a permission (`clients:read` to read, `clients:projects` to write, `system:write` for the settings). One side's cookie is nothing on the other's. | `routes.ts`, `admin.ts` | `communicationsSecurity.test.ts` ("every address answers a stranger 401…", "an editor works on conversations…") |
| **CSRF / cross-site** | Every change needs the session's own CSRF token **and** a same-origin request; no CORS header is sent; cookies are the existing `HttpOnly`, `SameSite` session cookies. | the existing portal/admin session layer | "a change without the session's own token, or from another site, is refused, and nothing is written" |
| **Believing the request** (mass assignment) | Bodies are read **field by field** (`exact()`): an unknown key is refused. Sender, customer, status, visibility, importance and type are never taken from a body: the sender is the session, a customer's message is always a customer-visible text. | `input.ts` | "who writes, which customer, which status and what is visible are never believed from a request" |
| **Private notes leaking** | See MESSAGE_VISIBILITY.md: SQL-level filter on every customer read, database `CHECK`s and triggers, no text in e-mails or logs. | `views.ts`, migration 0015 | the visibility tests listed there |
| **SQL injection** | Every value is a bound parameter; `LIKE` wildcards in a term are escaped; the only text interpolated into SQL is fixed fragments, enforced by the static-SQL rule in `security.test.ts`. Filters are checked against fixed lists or plain ids first. | `search.ts`, `views.ts` | "hostile text in a query, a filter, a cursor, a reference or a number is answered as text, never as SQL"; "treats what is typed as text"; the static SQL test |
| **XSS** | Messages are **plain text**, stored as typed and rendered by React as text (`dangerouslySetInnerHTML` is not used in any conversation screen; links are not made from the words). E-mails carry no message text. Responses are JSON with `X-Content-Type-Options: nosniff`; the existing CSP applies. | the screens, `communicationTemplates.ts` | "markup, scripts and quotes are stored and returned as the text they are; nothing in a conversation is ever run"; the SSR component tests; the journey's browser-error check |
| **Brute force / flooding / scraping** | Rate limits by address: `messageSend` 40 per 10 minutes, `messageSearch` 20 per minute, on top of the portal's and the administration's own limits. A customer can leave at most 10 threads waiting and have 300 threads; a thread holds at most 2000 messages. | `rateLimit.ts`, `service.ts` | "sending and searching have their own limits, and reading is not stopped by them"; "a customer cannot leave more than ten conversations waiting"; "a thread holds a few thousand messages at most" |
| **Oversized or malformed input** | Body limit of the server (64 KiB by default); a message is 1 to 4000 characters, a subject 1 to 200, a search 2 to 100; control characters are refused; a cursor, limit or sequence number must be a well-formed number or token. The database refuses a body over 5000 as a last line. | `service.ts`, `search.ts`, migration | "validates what is written…", "a message is words and no longer than a few thousand characters…" |
| **Double submits / retries / races** | Every send carries a `clientToken`: the same send twice is one message (unique index + lookup). Status changes carry the revision the screen saw (a stale one is `409`). Every act is one transaction on a conversation read again inside it. | `service.ts`, migration | "sending the same message twice stores it once", "concurrent messages all arrive, each once, in a strict order", "two administrators changing the status from the same screen: one wins" |
| **Tampering with history** | A message is never changed: not its sender, type, visibility, time or order; the owner's own private note may be edited, the owner's own message removed (a tombstone). A customer's message is never removed or edited by anybody. A read marker never moves back. | database triggers | "a message is never changed, a removed one stays removed…" |
| **Caching / indexing** | Every answer is `Cache-Control: no-store`; portal and admin pages are `noindex, nofollow` and `no-referrer`; the pages are not in the sitemap and not measured by analytics. | `security.ts`, existing portal rules | "every answer is private: not cacheable, not shared with another site, not guessable as another type"; the SEO checks |
| **Sensitive content in e-mail, logs, errors** | An e-mail carries no message text, no subject, no note. Log lines carry kinds and route patterns. Validation errors name the field and a reason code (`tooLong`), never the value. The audit trail records ids and kinds, never what was written. | `communicationTemplates.ts`, `admin.ts` | "carries no word of what was written…" |
| **A switched-off customer** | Takes no message from either side and gets no e-mail; the owner can still write a private note. | `service.ts`, `notify.ts` | "a customer who was switched off is written nothing and cannot be written to" |
| **Erasure** | Erasing a customer deletes their conversations, messages, markers, e-mail choices and the e-mails about them. | `customers/retention.ts` | "erasing a customer removes their conversations, their messages and the e-mails about them" |
| **Owner's actions** | Every write is in the audit trail (`communications.started`, `.reply`, `.announcement`, `.note`, `.status`, `.removed`, `.note_edited`, `.settings`) with ids, never words. | `admin.ts` | the owner-side tests |

## Attachments: deliberately not built

The brief allowed attachments **only if secure private storage already exists**. It does not:

* The media library stores the **public site's pictures** under public URLs.
* Customer documents (`client_documents`) are a disabled feature: there is no secure private file store, no access-controlled download route, no scanner, no quota.

So a message is **words only**, the composer says so, and nothing in the database or the API has a place for a file. **What would have to exist first:** a private object store (not a public folder) with per-customer keys; downloads through an authenticated route that re-checks ownership on every request and sends `Content-Disposition: attachment` with `nosniff`; an allow-list of types checked by content, not by name; a size and a per-customer quota; malware scanning; a retention rule and erasure that deletes the files; and a decision about e-mail (links only, never the file). Until the owner decides that, a customer who needs to send a file should be told so in a message, and the file should travel by another channel the owner chooses.

## What is not protected against

* **The owner (and any administrator with `clients:read`) can read every conversation and every private note.** There is no end-to-end encryption and no per-conversation access list.
* **Data at rest** is the same SQLite file as everything else, with the protection the host gives it. Backups and their encryption are the earlier prompts' and the host's matter; the words of removed messages **stay** in that file.
* **A proxy in front of the application** (Render, Cloudflare) may log full request addresses, including a search term in a query string. That is the host's logging setting.
* **Spam, abuse and abusive content**: only the rate limits and per-customer caps exist; there is no content moderation, blocklist or CAPTCHA. By default a customer account exists only by the owner's invitation, which is the real gate. **If the owner switches on the portal's open registration (*anyone who proves an e-mail address may create an account*) and also *Customers may start conversations*, anyone who can read an e-mail address can write to the owner**; the per-customer caps and the rate limits limit that, they do not prevent it. Keep one of the two off unless that is intended.
* **Phishing in a customer's own words**: a message is plain text and links are not made clickable, but nothing stops a customer (or someone with a stolen session) from writing a link as text.
* **Stolen sessions and compromised mailboxes**: a sign-in link goes to the customer's mailbox; whoever controls it controls the conversations. The portal's own session rules (expiry, revocation) apply; nothing new was added.
* **Timing and enumeration**: references are random, and not-yours and not-found are the same answer, but response *timing* was not measured.
* **No penetration test and no independent security review** has been done. The measures above are tested by this repository's tests, which prove what they assert and nothing more.
